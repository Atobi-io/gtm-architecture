The Engine Pattern

The reusable blueprint for building engines in any domain
Distilled from gtm-engine-architecture-v3.2 · 2026-07-24
What this is

The generic blueprint for building engines: the core structures every engine is built from, and where the pattern fits. Use it when designing an engine for a new domain.

The fit

Where It Fits

Each structure in the blueprint pays off only under certain conditions. Together they draw a precise map of where an engine is worth building.

The four conditions

Four conditions decide the fit. None of them is a hard requirement, but the more of them hold, the more of the pattern pays off:

  1. One body of knowledge, many outputs. Foundation is expensive to build and cheap to read. It pays off only where many outputs draw on the same slowly-changing knowledge (voice, positioning, audience, proof). If every task needs fresh, unique knowledge, Foundation gives no leverage.
  2. Rhythm, not one-offs. Cron, queue, cadence plans and catch-up logic are built for recurring work. The value accumulates per repetition; a one-off project never amortises the setup cost.
  3. Output that represents someone. The voice layers, the voice gate and the humanizer exist because the output goes out into the world and sounds like a person or a brand. If the output is purely transactional (invoices, data extracts), the gates are overkill and simpler automation wins.
  4. Lasting relationships with observable reactions. Signal harvesting and accumulating scores assume the same recipients recur and their reactions can be seen. Without recurring relationships or a feedback channel, the whole signal layer stands still.
Three levels of fit
  • Full fit (all four): go-to-market, customer success, content and brand, employer branding, partner and investor communication. The shared shape: one knowledge base, many sends, recurring recipients, measurable reactions.
  • Partial fit: a strategy engine is strong on knowledge + production + the learning loop, but the delivery and signal layers sit nearly idle (low cadence, internal audience). Async support (tickets) can fit; real-time dialogue cannot.
  • Poor fit: one-off deliverables, real-time conversation, and output where correctness dominates over voice.

The litmus test: does the function repeatedly turn one body of knowledge into communication to people whose reactions it can learn from? Then it is engine-shaped.

The blueprint

The Core Structures

Six groups of building blocks every engine is assembled from: what it is, how it is governed, why its output is good, how it sees, why it lasts, and what makes it reusable.

Anatomy

What an engine IS

  • Foundation as the read-surface. All knowledge about the subject (voice, positioning, audiences, proof) lives in one place, and every skill reads from it at runtime. Nothing is hardcoded.
  • Three layers: Knowledge → Production → Delivery. What the engine knows, what it produces, and how it reaches the recipient are strictly separated, so each layer can be improved without touching the others.
  • One unit of work, no special cases. Everything the engine drives is the same kind of object with the same contract chain (brief + plan), in only two variants: timebound or ongoing. So all mechanics (queue, portfolio, reporting) work on everything, and the engine does not grow in complexity as initiatives are added.
  • Contracts between the layers. Each layer hands over a defined format to the next, never loose text. So the layers can be developed and tested independently.
  • New channels are built from a template. A new output channel is made by copying a fixed pattern and filling in the channel’s details, not by writing new engine code. That makes adding output channels very easy.
Human + machine

How it is governed

  • The approval queue as the single meeting point. The engine produces, the human approves in one surface, and nothing goes out without approval where it matters.
  • Approval has one home. One field in one file is the truth about “approved”; everything else is a mirror. No double bookkeeping.
  • The learning loop. The human’s corrections graduate into Foundation via skills, so the engine gets better from being corrected instead of repeating the mistake.
  • Roles and authority. Owner, coordinator and operators with clear boundaries for who may do what. Scales from one person to a team.
  • Portfolio management. Hard ceilings and overlap checks across active initiatives, so multiple initiatives do not cannibalise each other.
Voice and quality

Why the output is good

  • Two-layer voice. Voices are separate artefacts layered on top of each other: company + person (the operator sounds like themselves, grounded in the company’s voice) or company + brand (the company writes as itself, but within a brand’s guidelines). All output sounds like a human, not like “the system”.
  • Voice gate on all output. Nothing leaves the production layer without being checked against the voice profile and its anti-patterns.
  • Humanizer as a fixed step. The de-AI pass is part of the contract, not an afterthought.
  • Recipient verification before sending. The engine double-checks that what it sends goes to the right person. Never the wrong one.
Signal and intelligence

How it sees

  • Signal harvesting from the outside world. The engine picks up reactions to what it sends out, evaluates them against its knowledge of what matters for that particular engine, and surfaces what deserves action as suggestions to the human.
  • Scores that accumulate over time. Signals are logged per relationship, so patterns become visible instead of forgotten between sessions.
  • Relationship state is coded knowledge. The engine knows who is new, active or a past relationship, and behaves differently towards each.
Operations and robustness

Why it lasts

  • Runs on its own schedule. Cron-driven, headless, with notifications when there is something new for the human. The engine does not wait for anyone to remember it.
  • Auto-delivery with per-channel gates. Approved output is delivered automatically; each channel has its own gate that can be opened gradually as trust grows.
  • Write boundaries enforced by hooks. Knowledge artefacts cannot be hand-edited, and engine code cannot be changed outside the build discipline. Discipline is code, not agreements.
  • Migrations register + versioning. Every installed instance is updated with numbered, idempotent steps. One engine core, several instances, all in sync.
  • Build queue. Ideas are captured as specs and built serially in a dedicated build session, so development never disturbs operations.
The design principles

What makes it reusable

  • Subject-agnostic by design. The engine does not know its subject; it reads it at runtime. Same engine + new Foundation = new engine.
  • Knowledge separated from mechanics. Everything domain-specific lives in knowledge artefacts, all mechanics in skills. So the mechanics can be reused 1:1 across domains.
  • The ownership rule. Everything the engine depends on, it owns itself; shared utilities are composed. No silent breakage from outside.
  • General solutions, never point-in-time. Every feature is built as the general case, so the next engine inherits it for free.
  • The architecture learns across engines. The engine is one shared core, and every engine is an instance of it. When work on one engine makes us smarter, the improvement is built into the core and rolled out to the others via versioned updates. Learning in one place lifts all.
The consequence: a new engine is a new Foundation plus a selection of channels, not a new system. The mechanics, the discipline and the learning loops come along from day one.
